# Panel-to-Coolify migration

Move the user's required traffic and retire the panel without losing data or disabling services still in use. Work quickly: batch read-only checks into a small number of SSH calls, inspect only relevant details, reuse evidence, and give concise updates. Do not claim zero downtime or guaranteed recovery. Follow the user's accepted maintenance window, backup scope and other instructions; prior authorization remains valid.

The generic cutover and panel-retirement scripts are **planning-only**. They refuse `--apply` because they cannot prove a given server's dependencies or provide an independent watchdog. Do not work around that refusal: prepare, review and use server-specific actions. See [safety invariants](references/safety-invariants.md) and [panel differences](references/panels-matrix.md) when needed.

## Fast path: minimum checks, then act

Use one or two batched SSH calls per phase where practical. Do the following once; go directly to the authorized action when the conditions are met:

1. Identify the public listener, required routes/upstreams, intentionally stopped projects, running application image/data mounts, and any panel/Apache/PHP/certificate dependencies relevant to the requested change. Check representative required endpoints and the existing Coolify configuration.
2. Respect the already agreed backup scope and downtime. Prepare a concrete independent rollback that restores the actual previous state; verify it to the extent necessary for this server. Do not request approval again or create a full backup when the user declined it.
3. Switch only what needs switching and check the critical public routes and services. Retry a transient failure once by default, preserve the first result, and investigate further only if it persists or other evidence warrants it. Confirm or trigger the prepared rollback within its deadline.
4. For panel retirement, inspect exact packages, package scripts/conffiles, required live services and jobs; simulate the exact package operation, perform the reviewed change, and recheck affected routes/services. Stop when finished and report the outcome.

Avoid repeated inventories, full-domain reruns, speculative tests, heavy stages or automatic subagents. Add a check only to resolve a specific unknown or failure, or because the user requested it. Reuse current evidence, and do not restart working services merely for proof.

## 1. Inventory and agree the target

- Run `scripts/preflight-inventory.sh [--public-ip IPV4] [--dns-limit N]` over one SSH connection, then inspect only gaps. It avoids intentionally changing services; connections and ordinary commands can still create logs. Discovery and DNS output are incomplete, and an unresolved lookup is not proof a domain is dead. The public IPv4 must be supplied rather than guessed from the server's egress address. Check A and AAAA externally and account for NAT and CDN routing before ACME.
- Build a compact map: required and intentionally inactive domains, aliases, current response/redirect/TLS baseline, upstreams, public TCP/UDP listeners, proxy/container/host services, and data/mount paths. Normalize internationalized names to ASCII/Punycode when required; preserve the intended Unicode display name and verify aliases and certificate SANs. Do not treat a pre-existing 502 as a new regression or revive an excluded project.
- Trace live dependencies before modifying anything: current container image and labels, host vhosts, Apache/PHP, `.htaccess`, uploads, mutable container layers, database instances, cron/workers, mail, FTP, TLS paths and SSH. A name or listening socket alone does not establish that an application is healthy. Do not rebuild a running image from a branch whose code may differ; compare image metadata, worktree and remote history first and preserve existing runtime data and secrets.
- State the plan, downtime expectation, backup scope, side effects and remaining unknowns. Existing user approval is enough; ask only for missing decisions. Never fabricate a complete backup or a recovery point.

## 2. Recovery and verification plan

- Agree what to save and where before copying: a user may decline a full backup or request selected databases only. Preserve the minimum configuration, package/service state and rollback artifacts needed for the authorized operations; verify space, confidentiality and integrity. A host database dump is not a backup of a separate container database. If the user declines a safety measure, explain the concrete recovery limitation and proceed only within that choice; do not silently make a full copy. `scripts/backup-state.sh` is an **optional config/certificate snapshot**, contains private keys, and must not be described as a full backup.
- Protect databases, mail, FTP, SSH, firewalls, `/var/www`, user directories, live certificates and persistent volumes. Retain any Apache, PHP, nginx or generated panel configuration required by a working site. Use independent management access and a rollback that restores the **previous** running/enabled state, ports, process managers and routing; do not blindly start services that were previously stopped.
- Before switching a public listener, prepare and review a server-specific, idempotent rollback and an independent watchdog that survives SSH/shell failure; explicitly define timeout, confirmation and behavior after reboot, delayed Docker actions, partial changes and prior confirmation. Verify actual port owners and health, not just container status or whether `bind()` succeeds. Test the recovery path appropriate to the risk and state what was actually exercised. `scripts/cutover-and-rollback.sh --dry-run` prints a plan only; its `--apply` and `--rollback` refuse to act.
- Prefer existing working Coolify workloads and small, targeted checks. A separate VM or a heavy Mac-hosted stage is not automatically required; use safe local/loopback validation or a brief user-approved outage when appropriate. If equivalent pre-cutover evidence or recovery cannot be obtained, describe the specific gap and risk rather than repeatedly rebuilding elaborate testbeds.

## 3. Route, TLS and cut over

- Validate syntax and actual routes/redirects against their pre-migration baselines, including representative APIs and existing upload reads. `scripts/stage-verify.sh` verifies TLS chain and hostname by default, keeps the original Host/SNI with nonstandard destination ports, and does not follow redirects. `--cacert` supports private staging CAs; `--insecure` is diagnostic only and cannot write a receipt. An HTTP 200, a file read or a route receipt does **not** prove authentication, database writes, upload creation, WebSockets or business behavior. Accept a user's direct confirmation of a real workflow as user-reported evidence, without requesting a token for that same check; label its source and report other untested paths.
- Separate panel-managed certificates and challenge paths from panel removal. Verify the chosen renewal mechanism, DNS and HTTP-01/TLS-ALPN routing, certificates actually served, mount visibility and reload/publish behavior; use Let's Encrypt staging or another safe test where appropriate, avoid forced production reissuance and rate limits. A no-op `renew` is not proof of a new issuance. Avoid pinning renewal to a container ID that changes on normal recreation without safely revalidating the replacement.
- Preserve custom Coolify proxy configuration in Coolify's own saved configuration, not only in `/data/coolify/proxy/docker-compose.yml`; a UI restart may rewrite disk-only changes. Compare the saved and active configuration, networks, trusted proxy addresses, published ports, dynamic routes and certificate mounts. Test/review lifecycle behavior without restarting live services merely to prove a point.
- With the authorized window and recovery mechanism ready, switch only the public listeners and necessary workers. Never create duplicate stateful workers merely for a check. Coolify or another actor can deploy or recreate a proxy concurrently: capture the initial result and relevant container/deployment state, retry transient failures only a bounded number of times and record both outcomes. Do not hide failures or label a one-off deployment interruption as a permanent failure. Keep retries within the rollback deadline. Compare live results to baseline and confirm the independently controlled rollback before its deadline; on a critical new failure, invoke the prepared recovery. Record which checks passed, failed or were not run.

## 4. Retire the panel after live verification

- Respect the user's request to remove it and existing approval, but first determine what the panel still manages. Account for its webmail/phpMyAdmin, scheduled backups, certificate jobs, databases, SSH CA, user sites, host vhosts and panel-generated configuration. Preserve anything still required; paths with a panel name can remain essential.
- `scripts/purge-panel-safe.sh --panel fastpanel2` is a **read-only plan**, including an APT removal simulation where available. It does not attest to safe removal and refuses `--apply`. Never run wildcard purge, `autoremove`, or recursive deletion of panel directories blindly. For an authorized server-specific removal, enumerate exact packages, simulate the exact operation, inspect package maintainer scripts and package-owned conffiles (including files under `/var/www`), compare the complete transaction to the reviewed plan, and stop only the unused panel units. Archive or retire only panel-owned jobs shown to be obsolete. Unknown dependencies are a reason to stop, not to guess.
- Verify from outside and on the host after changes: required routes and TLS, actual proxy/listener ownership, preserved service states, package result, relevant config/data integrity and renewal. If an authenticated/write check or a reboot/recreation was not exercised, say so. Keep the report brief: what changed, what was checked, retained dependencies, and material limitations.
